\section{About BitBucket Cloud}

BitBucket Cloud is an cloud-hosted, multi-tenant SCM that is often confused with \intlink{sec:bbdc}{BitBucket Data Center};
while the name of the products imply that they are the same, they are completely different products
with different repository topologies and features. This section covers configuring \cxoneflow
for use with BitBucket Cloud.

The \cxoneflow endpoint \texttt{/bbc} is the handler for all webhook event
payloads originating from BitBucket Cloud.

\section{Webhook Configuration}

The webhooks for BitBucket Cloud can be configured at the workspace scope
\footnote{The BitBucket Cloud UI does not have a guided way for workspace deployment of webhooks;
use \cxoneflowaudit for assistance with workspace webhook deployment.} or at repository scope.
For large enterprise deployments with many repositories, deploying at the repository scope
is likely infeasible.  The recommended approach is to deploy the webhooks at the workspace scope
so that webhook events are sent for all repositories in the workspace.  This will prevent the need
for a periodic check that repositories are sending events to \cxoneflow since any new repositories
will be onboarded to \cxoneflow automatically.

While repositories are segregated by projects in a workspace, BitBucket Cloud enforces a unique
repository name across all repositories in the workspace regardless of project membership.  The
project identifier is therefore not included in the clone URL that is used by \cxoneflow for routing
to the correct service definition.  The clone URL contains the workspace identifier to allow
routing by workspace but the credentials for API access and cloning should allow access to all
repositories in the workspace.

Figure \ref{fig:bbc-token-config} shows the \texttt{connection} element configuration required
for BitBucket Cloud to work with \cxoneflowns.  Note in the configuration:

\begin{itemize}
  \item The \texttt{base-url} is \texttt{https://api.bitbucket.org}
  \item The \texttt{api-url-suffix} is set to \texttt{2.0}
  \item The \texttt{base-display-url} is set to \texttt{https://bitbucket.org}
\end{itemize}


\section{Authentication Configuration}

There are several options for authenticating with BitBucket Cloud for API and clone
access.  Premium subscribers will be able to create \textit{Access Tokens} that
allow for a simple authentication configuration.  Non-premium subscribers can use
\cxoneflow with BitBucket Cloud but the authentication configuration is slightly
more difficult.

BitBucker Cloud users, regardless of subscription type, can create \textit{API Tokens} that
are roughly equivalent to \textit{Personal Access Tokens} used by other SCMs.  The token
is associated with the user account; if the user is deleted from the organization, the token
is no longer valid.

BitBucket Cloud also supports SSH keys for cloning.  In some configurations, they are
named \textit{SSH Keys} and in others they are named \textit{Access Keys}.  All subscribers
may install an SSH key at the \textbf{Workspace}, \textbf{Project} and
\textbf{Repository} scope to allow clone access to all workspace repositories.
It should be understood, however, that the SSH key will have both read and write access
to a repository accessed by \cxoneflowns.  \cxoneflow does not require write access to a
repository for scan orchestration; \textit{Access Keys} and \textit{API Tokens} can be scoped
to allow read only access to repositories.

\textit{Access Tokens} that are not associated with a user account are the recommended
method of configuring \cxoneflow to enable both cloning and API access.  For premium
subscribers, access tokens can be created in both the \textbf{Workspace} and \textbf{Project}
settings.  For all subscribers, access tokens can be created in the \textbf{Repository} settings.
Table \ref{tab:bbc-access-tokens} explains how the access token configuration affects
the visibility of repositories.


\begin{table}[ht]
    \caption{BitBucket Cloud Access Tokens Scope}  
    \label{tab:bbc-access-tokens}      
    \begin{tabularx}{\textwidth}{ll}
        \toprule
        \textbf{Configuration} & \textbf{Description} \\
        \midrule
        Workspace & \makecell[l]{This is the recommended configuration location for a token used
        with\\\cxoneflow. An access token created here will have visibility to\\
        all repositories in the workspace.}\\
        \midrule
        Project & \makecell[l]{An access token created here will have visibility to repositories\\
        in the project where the token is created.  A token created at this\\
        scope is not recommended unless there is only one project.}\\
        \midrule
        Repository & \makecell[l]{An access token created here will have visibility to
        only the\\repository where the token was created.}\\
        \bottomrule
    \end{tabularx}
\end{table}

Using access tokens created in the project or repository settings with \cxoneflow will
make configuration of SCM service definitions difficult.  The reason is that the 
routing configuration will not be able to discern which project a repository belongs
to when handling a webhook event.  For both project and repository tokens, the routing
configuration must use the name of the repository.  Configuring an SCM service definition
for each repository will likely not scale and may cause a performance impact on
\cxoneflow operations.

All tokens can be assigned scopes that allow actions to be executed by \cxoneflow.  The
required scopes for \cxoneflow operation with BitBucket Cloud
\footnote{Token creation in BitBucket Cloud will allow scope definition for other Atlassian Products
that are not accessed by \cxoneflow.  Ensure that scopes are selected for BitBucket.}
, regardless of token type, are:

\begin{itemize}
  \item read:repository:bitbucket
  \item read:pullrequest:bitbucket
  \item write:pullrequest:bitbucket
\end{itemize}

\subsection{Configuring \cxoneflow with API Tokens}

Figure \ref{fig:bbc-api-token-config} shows a configuration using an \textit{API Token}.
These types of tokens are tied to a user account and are available to all subcribers.
Using this type of authentication requires the use of both the \texttt{api-auth} and
\texttt{clone-auth} configuration elements.  The \texttt{password} configuration element
is a secret containing the \textit{API Token} and is the same for both the \texttt{api-auth}
and \texttt{clone-auth} configurations.

In the \texttt{api-auth} configuration, the \texttt{username} secret must be the full email
address of the user account that owns the token.  Authentication with the API will fail
if the full email of the user account is not used.

In the \texttt{clone-auth} configuration, the \texttt{username} secret is the BitBucket Cloud
"public name" found on the account profile; this is not the full email address of the user account.
The public name is what is displayed when viewing commit logs, clone URLs, and pull-request comments.  

If not using \intlink{sec:scan-agents}{Scan Agents} with \cxoneflow, it is possible to use
an \textit{Access Key} for SSH cloning.

for clone authentication.  This configuration can be used with an SSH key installed
at the \textbf{Workspace} scope to allow cloning for all repositories in the workspace.
SSH does not provide authentication for API access, so an \textit{API Token} must be used.

This configuration is only suggested as an option for edge cases where an SSH key must be used
for cloning.  The recommended method for both API access and cloning is to use

\section{Protected Branches}

The \textit{Branching Model} is used by \cxoneflow to determine which branches
should be treated as protected branches.  Figure \ref{fig:bbc-branch-model}
shows an example of a \textit{Branching Model} with both a production and
development branch.  Both the production and development branch are considered
to be protected branches by \cxoneflow.

A \textit{Branching Model} applied at the project level will make the branches used
by all the repositories in the project use the same branch names for production and
development.  The \textit{Branching Model} configuration can be overridden by
a repository configuration; \cxoneflow allows BitBucket Cloud to apply overrides
to provide the effective protected branches for each repository.

\section{Policy Integration with Branch Restrictions}

If the configuration element \texttt{feedback.pull-request.use-policies} is set to
\textbf{true}, scan status is written to the pull request.  Figure \ref{fig:bbc-policy-check}
shows an example of a status written to a pull request upon a successful scan that
was evaluated with no policy violations. The name of the displayed check can be set to a
custom value with the \texttt{bb-pr-opts.check-name} configuration element.

Using \textit{Branch Restrictions}, this policy check can be used to block
the merge of the pull-request until a successful scan has completed with no policy
violations.  Figure \ref{fig:bbc-branch-restriction} shows an example of a
\textit{Branch Restriction} that would prevent merging the pull request to a protected
branch.  Without the use of \textit{Branch Restrictions}, the scan status update written
to the pull-request is informational only.
